# AI 朗读机需求与当前设计方案

## 1. 项目背景

当前要做的是一个面向学生的 AI 朗读机 / 阅读陪练功能。

在当前版本中：

* 暂时不上 RAG
* 前端预置若干篇文章供学生选择
* 学生选择文章后，系统获得该文章的结构化信息
* 系统围绕该文章与学生进行多轮问答
* 对话目标是帮助学生理解文章内容，并提升语言能力

当前文章数据示例：

* 文章标题：少年閏土
* 文章作者：魯迅
* 文章语言：香港繁体中文
* 文章内容：文章全文

---

## 2. 核心需求整理

### 2.1 业务目标

系统需要扮演语言学习老师，围绕学生当前所学文章进行多轮引导式提问，帮助学生：

* 理解文章内容
* 掌握细节信息
* 理解文章主旨与深层含义
* 提升表达能力
* 在语音交互场景下完成自然、简洁、稳定的对话

### 2.2 对话要求

* 提问语言根据文章语言决定

    * 香港繁体中文文章：使用香港繁体中文提问
    * 英文文章：使用英文提问，且词汇难度需根据文章内容调整
* 角色定位：语言学习老师
* 对话目标：通过提问帮助学生理解文章内容，提高语言能力
* 问题需要有针对性，并从浅到深推进
* 问题类型包括：

    * 细节理解
    * 主旨大意
    * 推理判断
    * 词汇理解
* 每轮提问后等待学生回答，再根据回答进行评价、追问或引导
* 每轮输出控制在 3-5 句话以内
* 风格要友好、鼓励、清晰，适合学生水平
* 输出必须适合智能语音播报

### 2.3 严格限制条件

* 只能基于文章内容进行提问、评价和引导
* 不能使用任何外部资源或外部知识
* 不能超出文章范围进行发挥
* 输出中不得包含：

    * 制表符
    * emoji
    * 不可见字符
    * HTML
    * Markdown 格式控制字符
* 学生回答来自语音识别，可能有识别错误或同音字，系统需要结合上下文自动理解和校正
* 不能使用图片、视频、音频等媒体资源参与回答内容生成

---

## 3. 架构选择结论

## 3.1 不建议使用完整 ReAct Agent

当前场景不适合采用完整的 ReAct Agent 设计，原因如下：

1. 任务本质是受控教学对话，不是自主执行任务

    * 不需要调用外部工具
    * 不需要搜索外部信息
    * 不需要自主规划复杂动作链
    * 不存在网页操作、文件处理、接口联动等外部执行任务

2. 业务流程天然固定

    * 提问轮次明确
    * 每一轮目标明确
    * 只需要围绕文章内容推进问答
    * 不需要模型自主决定整个流程

3. ReAct 会增加不必要复杂度

    * 增加 Prompt 复杂度
    * 增加上下文长度与 token 成本
    * 增加响应延迟
    * 降低输出稳定性

4. 语音交互场景更强调稳定、简洁、低延迟

    * 朗读机需要快速响应
    * 输出需要高度受控
    * 不适合引入多余的推理过程和行动决策层

## 3.2 推荐方案：状态机 + 一问一答

当前最适合的方案是：

状态机 + 单轮 LLM 生成 + 后端控流程

也可以理解为：

* 前端负责文章选择、语音输入、播报和展示
* 后端负责维护会话状态和轮次推进
* LLM 只负责生成“这一轮老师应该说的话”

这不是自由聊天，也不是完整 Agent，而是一个受控的多轮教学对话系统。

---

## 4. 整体交互设计

## 4.1 总体原则

整个系统的核心原则是：

前端负责控交互，后端负责控状态，LLM 负责生成当前轮回复。

也就是说，模型不负责控制整个产品流程，业务代码才是流程控制者。

## 4.2 基本交互流程

### 第一步：学生选择文章

前端展示若干篇预置文章。
学生选择其中一篇后，前端拿到文章信息：

* articleId
* title
* author
* language
* content

这一阶段不需要调用 LLM。

### 第二步：初始化会话

后端创建阅读会话，保存当前会话信息，例如：

* sessionId
* articleId
* articleTitle
* articleAuthor
* articleLanguage
* articleContent
* currentRound = 1
* history = []
* status = in_progress

然后后端发起第一次 LLM 请求，用于生成第一轮问题。

### 第三步：生成第一轮问题

后端调用 LLM，要求模型：

* 基于文章内容
* 使用文章对应语言
* 提出第一个问题
* 问题聚焦文章主题或主要内容
* 输出适合语音播报

LLM 返回老师第一轮要说的话。

前端展示文字并调用 TTS 进行播报。

### 第四步：学生回答

学生通过语音作答。
前端将语音送入 ASR，得到识别文本。

### 第五步：提交学生回答

前端将以下信息发送给后端：

* sessionId
* 当前学生的 ASR 识别文本
* 可选的语音元信息

### 第六步：后端生成下一轮回复

后端读取当前会话状态，组织本轮 LLM 输入，包括：

* 当前文章
* 当前轮次
* 上一轮老师问题
* 学生本轮回答
* 历史对话摘要或最近几轮对话
* 当前轮次的任务目标

然后调用 LLM，让模型生成：

* 对学生回答的简短反馈
* 当前轮的追问，或下一轮的新问题

### 第七步：继续推进直到结束

重复执行以下循环：

* 学生回答
* 后端更新状态
* 调用 LLM 生成下一轮老师话术
* 前端展示并播报

直到完成最后一轮总结，结束会话。

## 5. 推荐的轮次设计

建议将整个阅读陪练过程设计成固定 5 轮结构，由后端状态机控制。

### Round 1：基础理解

目标：帮助学生理解文章主题、主要内容、主要人物或整体场景。

### Round 2：细节理解

目标：考察学生是否能说出文章中的具体细节、人物行为、事件内容等。

### Round 3：深层理解

目标：考察学生对文章含义、人物形象、作者意图或情感表达的理解。

### Round 4：问题引导与纠偏

目标：针对学生前面回答中的问题进行进一步引导。
可能包含：

* 纠正偏题
* 引导补充
* 帮助学生表达得更完整
* 处理语音识别导致的歧义

### Round 5：总结与巩固

目标：对整段学习过程进行总结，强化学生对文章的理解，并给予鼓励性反馈。

说明：

* 轮次结构由后端程序控制，不建议完全交给 LLM 自主决定
* 允许在单轮内部做一次追问，但整体轮次最好仍由后端掌控

---

## 6. Prompt 分层设计

## 6.1 SystemPrompt 放什么

SystemPrompt 应放长期稳定、跨会话通用的规则，包括：

* 角色定位
* 对话目标
* 输出风格
* 输出约束
* 语言要求
* 不能使用外部知识
* 语音播报适配要求
* 处理 ASR 错误的要求

SystemPrompt 负责定义“你是谁”和“你必须怎么做”。

## 6.2 UserPrompt 放什么

UserPrompt 应放本轮动态输入，包括：

* 文章标题
* 文章作者
* 文章语言
* 文章内容
* 当前轮次
* 学生上一轮回答
* 当前轮任务
* 最近几轮上下文

UserPrompt 负责定义“你这一次面对的具体内容是什么”。

## 6.3 文章内容应该放在哪

结论：文章内容应放在 UserPrompt，而不是 SystemPrompt。

原因：

1. 文章内容属于动态业务数据，不是长期规则
2. 前端会切换不同文章，文章天然是会话输入
3. 后续每轮还会拼接学生回答、轮次信息、任务目标，这些都属于同一层动态输入
4. 将文章放入 System 层会导致职责混乱，不利于维护

因此：

* SystemPrompt：固定规则
* UserPrompt：文章 + 当前轮任务 + 学生回答

## 6.4 首轮调用方式

当学生选择文章后，后端可以立刻发起首轮请求。

首轮请求中：

* SystemPrompt：固定规则
* UserPrompt：文章信息 + 当前轮次 = 1 + 当前任务 = 提出第一个问题

LLM 返回老师的第一轮问题。

因此，不需要把文章内容塞进特殊的 <SystemReminder> 标签并放入 SystemPrompt 中。
当前设计中，更推荐保持 Prompt 分层清晰。

---

## 7. 后端状态机设计

推荐使用有限状态机或显式轮次推进方式，而不是 Agent 式自主规划。

可以定义类似状态：

* START
* ROUND_1
* ROUND_2
* ROUND_3
* ROUND_4
* ROUND_5
* END

每一轮状态都由后端控制进入和退出。

状态推进逻辑大致为：

1. 进入某一轮
2. 根据该轮目标构造 Prompt
3. 调用 LLM 生成老师当前轮输出
4. 等待学生回答
5. 处理学生回答
6. 判断是否继续追问或进入下一轮
7. 更新会话状态

这样设计的优点：

* 结构清晰
* 可控性强
* 易于做复盘与埋点
* 易于适配语音交互
* 易于做后期能力扩展

---

## 8. 推荐的数据结构

## 8.1 Session 级结构

建议一个阅读会话至少包含：

* sessionId
* articleId
* articleTitle
* articleAuthor
* articleLanguage
* articleContent
* currentRound
* status
* turns
* createdAt
* updatedAt

## 8.2 Turn 级结构

每一轮建议保存为结构化记录，例如：

* round
* teacherQuestion
* studentAnswerRaw
* studentAnswerNormalized
* teacherFeedback
* teacherFollowup
* action

其中：

* studentAnswerRaw：ASR 原始识别结果
* studentAnswerNormalized：系统基于上下文理解后的规范化表达
* action：本轮处理结果，例如 continue、next_round、end

这种结构有利于：

* 调试模型效果
* 做学习报告
* 做学生薄弱点分析
* 做后续个性化学习推荐

---

## 9. 单轮生成的推荐思路

每次调用 LLM 时，不要让模型自由发挥整轮会话，而是明确告诉它当前这一步要做什么。

例如，某一轮的输入应显式包含：

* 当前轮次
* 当前教学目标
* 学生本轮回答
* 是否需要反馈
* 是否需要追问
* 是否需要进入下一轮

这样可以显著提升：

* 输出稳定性
* 轮次控制能力
* 语言风格一致性
* 语音播报可用性

推荐的生成原则是：

* 每次只让 LLM 做一个小任务
* 每次只生成老师当前这一步要说的话
* 流程推进由代码决定，不由模型决定

---

## 10. 当前方案的总结结论

### 10.1 架构结论

当前阶段，最适合的不是 ReAct Agent，而是：

状态机 + 一问一答 + 单轮 LLM 生成

### 10.2 Prompt 结论

* SystemPrompt：放长期规则和行为约束
* UserPrompt：放文章内容、轮次、学生回答、当前任务
* 文章正文不建议放入 SystemPrompt

### 10.3 交互结论

整体交互流程为：

1. 学生选文章
2. 后端初始化 session
3. LLM 生成首轮问题
4. 前端播报问题
5. 学生语音回答
6. ASR 转文本
7. 后端结合当前轮次和历史生成下一轮回复
8. 重复直到总结结束

### 10.4 控制权结论

* 前端控制交互体验
* 后端控制业务流程和轮次状态
* LLM 只负责生成当前轮老师话术

这是一套受控教学对话系统，而不是一个自主决策型 Agent。

---

## 11. 后续可扩展方向

在后续版本中，可以逐步扩展以下能力：

1. 学生水平分层

    * 根据年龄或年级动态调整提问难度
    * 英文文章按词汇难度控制表达

2. 个性化引导

    * 根据学生历史作答情况动态调节问题深度
    * 记录常见理解误区

3. 词汇专项练习

    * 针对文章中的重点词汇进行解释和追问

4. 学习报告

    * 输出本次阅读中的表现总结
    * 标记学生掌握较弱的点

5. 引入 RAG

    * 后续如果文章来源变多，可以接入知识库或素材库
    * 但即使引入 RAG，核心交互形态仍然建议保持“状态机 + 单轮生成”

---

## 12. 一句话总结

这个 AI 朗读机当前最合理的设计，不是完整 ReAct Agent，而是一个由后端状态机驱动、由 LLM 逐轮生成老师话术的受控多轮阅读陪练系统。
